# Stage 3 in plain words: what we did, how, and why

When Stage 3 started, we had half a solution. Stage 2 had taught Qwen3-1.7B's tokenizer 10,000 new Urdu tokens, so a sentence that used to cost about 3.1 tokens per Urdu word now cost about 1.3. That is the "inference tax" this project is about, cut by more than half: fewer tokens means lower cost, faster generation and more room in the context window. But the model itself had never seen those tokens. Each new token got a starting vector made by averaging the vectors of the old pieces it replaced, which is a reasonable guess but only a guess. The result was a model that read Urdu cheaply and badly: its Urdu quality got clearly worse than the original's, and its score on Belebele, a reading-comprehension test, fell to the level of random guessing. A cheaper model that is worse is not a result, so Stage 3 had one job: teach the model its new tokens without losing the saving.

The way to teach a model new tokens is to let it read a lot of text that uses them, which is called continued pretraining. The difficulty was the hardware. Fully retraining a 1.7-billion-parameter model needs about 27 GB of GPU memory, and the free Kaggle GPU we use (an NVIDIA T4) has 16 GB. So we trained only two small things. The first was the 10,000 new token vectors themselves, kept in a separate tensor so that the model's original 151,669 vectors could not change by accident; we checked afterwards that they were bit-for-bit identical. The second was LoRA, small add-on matrices on every layer that let the rest of the network adjust to the new tokens without rewriting its weights. We trained in two phases: first only the new vectors for 100 steps, so they become sensible before anything else moves, then both together for 700 steps. Training the vectors first stops the LoRA layers from learning to work around bad vectors instead of fixing them.

The training text was Urdu Wikipedia, about 16 million tokens after cleaning, with 10% English Wikipedia mixed in. The English is there so the model keeps practising English and does not forget it while it learns Urdu. Before training, we removed every Urdu or English line that shared eight consecutive words with our test sets (FLORES and Belebele). That dropped 47 lines, and it matters: if the test sentences had been in the training text, the model could score well by remembering them, and every number afterwards would be worthless.

Running this on Kaggle meant planning around 12-hour sessions and a weekly GPU budget. We did a short smoke run first, which stopped training on purpose and resumed it, to prove that recovery works. A speed trial then found the fastest settings that fit in memory (about 850 tokens per second). The main run took about 9.4 hours and saved a checkpoint to a private Hugging Face repository every 50 steps, so a crash would cost at most half an hour, not the whole run. At the end, the trained pieces were merged back into a normal model file. That step checks itself: it refuses to save if merging changes the model's outputs by more than a tiny tolerance (the actual change was 0.00007), or if any original token vector changed.

Judging the result needed care, because the usual measures are unfair here. Loss per token, perplexity and tokens per second all depend on how big a token is, and our model's tokens are bigger than the original's. So we used bits per character, which measures how well a model predicts the same text one character at a time, whatever its tokenizer. We scored three models on exactly the same 1,000-sentence test sets: the original, the extended-but-untrained one, and the trained one. As a sanity check, the original model reproduced its earlier scores exactly. We also wrote down what success would mean before training started, so the result could not be argued into a win afterwards.

The main results were good. On FLORES Urdu, the cleanest test, the trained model scores 1.72 bits per character against 3.56 for the untrained one and 2.34 for the original. In other words, it predicts Urdu better than the model we started from, while reading the same text with 2.4 times fewer tokens. English was not harmed. Two results were not wins, and we report them as such. Belebele did not move (34.0% against 33.4%, well within its margin of error), so better text prediction has not turned into better reading comprehension. And because the trained model also read 16 million tokens of Urdu that the original never saw, we cannot yet say how much of the gain comes from the new tokens rather than from the extra reading. A "control run" that trains the original model on the same budget would settle that. It is built (notebook 11) but not run.

Finally, we made sure the model works where people actually run models. We converted it to GGUF, the format llama.cpp and Ollama use, and proved that llama.cpp splits text into exactly the same tokens as the original Python tokenizer: 2,041 of 2,045 test texts match, and the other 4 differ only because of a known Unicode-normalization quirk. We built compressed 4-bit and 8-bit versions calibrated on Urdu text, confirmed that vLLM serves the model on a GPU, and chatted with it locally in Ollama on the laptop at 9 to 13 tokens per second. This is where the real weakness showed up. Qwen3 can "think" before it answers, and our model, trained on plain encyclopedia text instead of conversations, usually ends its turn after thinking without giving any answer: 3 of 4 prompts failed that way in Ollama. With thinking turned off it answered every prompt, and its simple Urdu answers (the capital of Pakistan, the province of Lahore) were correct. But it also invented facts and repeated itself on open-ended requests. We expected this cost when we chose to train a chat model on plain text, and the documentation says so plainly. Along the way we made a mistake: we added an Ollama setting to turn thinking off, believing a quick test had confirmed it. The real test showed that Ollama ignores that setting for these files, so we removed the feature and recorded the correction.

So what Stage 3 delivers is a Qwen3-1.7B that reads Urdu more than twice as cheaply as the original and predicts it better, still handles English, and runs in llama.cpp, Ollama and vLLM, all measured and reproducible from the code and notebooks. It is not a polished Urdu chatbot, and it was never meant to be. Its purpose in this project is to be the "target" model for the drafter stage, where we build small, fast draft models that share its vocabulary and measure how much faster Urdu generation can get with speculative decoding. Before that, Stage 4 repairs the damaged thinking mode with a short instruction-tuning step on generated Urdu conversations, so the drafters are built on a model people could actually use. The other open questions are written down rather than hidden: the control run and the unchanged reading comprehension.
